# Upgrade guide — v0.5.x → v0.7.x

> **Audience**: app maintainers on `polysource/*: ^0.5` who want to
> jump to `^0.7`. The v0.6.x line is install-compatible with v0.5
> (no breaking changes); v0.7 introduced two BREAKING changes
> deliberately, both gating the v1.0 freeze ([ADR-011](../../adr/0011-pre-v1.0-freeze-checklist.md)).
>
> If you skipped v0.6 entirely, this guide covers v0.5 → v0.7
> directly — v0.6 added features without breaking anything.

## TL;DR

Two BREAKING changes:

1. `FilterCriterion::$operator` is now a `FilterOperator` enum
   (was: `string`). All call sites that construct or `match()` on
   operators need updating.
2. `BatchableDataSourceInterface` removed. Adapters that
   implemented it must extend `DataSourceInterface` directly.

Both are mechanical migrations. Expect ~30 min for a medium app,
~2 hours for an app with many custom adapters.

Plus a handful of additive improvements you can opt into (concrete
field types, empty-fields synth, …) — see [What you can drop](#what-you-can-now-drop)
below.

## BREAKING #1 — `FilterCriterion::$operator: string` → `FilterOperator`

### What changed

`Polysource\Core\Query\FilterCriterion::$operator` is now typed as
`Polysource\Core\Query\FilterOperator` (a backed enum, `string`
implements `BackedEnum::$value`). The old free-form `string` is
gone — PHPStan / IDE will refuse string literals.

### Why

ADR-011 item A4. Operators were docblock-validated only — easy to
typo. Adapters' `match($criterion->operator)` blocks couldn't be
made exhaustive. URL serialization remains string-based (the enum is
string-backed), so saved bookmarks keep working.

### How to migrate

1. **Add the import** wherever you reference `FilterCriterion`:

   ```php
   use Polysource\Core\Query\FilterOperator;
   ```

2. **Replace string literals in constructors**:

   ```diff
   - new FilterCriterion('status', 'eq', 'active')
   + new FilterCriterion('status', FilterOperator::Eq, 'active')
   ```

   The 12 canonical operators map 1:1 to enum cases:

   | v0.5 | v0.7 |
   |---|---|
   | `'eq'` | `FilterOperator::Eq` |
   | `'neq'` | `FilterOperator::Neq` |
   | `'gt'` | `FilterOperator::Gt` |
   | `'gte'` | `FilterOperator::Gte` |
   | `'lt'` | `FilterOperator::Lt` |
   | `'lte'` | `FilterOperator::Lte` |
   | `'like'` | `FilterOperator::Like` |
   | `'in'` | `FilterOperator::In` |
   | `'nin'` | `FilterOperator::Nin` |
   | `'between'` | `FilterOperator::Between` |
   | `'null'` | `FilterOperator::IsNull` |
   | `'notnull'` | `FilterOperator::IsNotNull` |

3. **Replace `match` cases in adapter DataSources**:

   ```diff
     match ($criterion->operator) {
   -     'eq' => $this->whereEq(...),
   -     'gt' => $this->whereGt(...),
   -     default => null,
   +     FilterOperator::Eq => $this->whereEq(...),
   +     FilterOperator::Gt => $this->whereGt(...),
   +     default => null,
     };
   ```

4. **When reading operator as a string** (URL encoding,
   serialization, Twig templates), use the `->value` accessor:

   ```diff
   - $url = '?op=' . $criterion->operator;
   + $url = '?op=' . $criterion->operator->value;
   ```

### Compatibility shim for libraries supporting both v0.5 and v0.7

If you maintain a library that needs to support both lineages,
detect the type at runtime:

```php
$op = $criterion->operator;
$opString = \is_string($op)
    ? $op
    : (\is_object($op) && property_exists($op, 'value') ? (string) $op->value : '');

if ('like' === $opString) {
    // …
}
```

This is the pattern used in the polysource OSS smoke tests that
boot against both `^0.5` and `^0.7` installs.

### URL backward compat

Saved bookmarks and shared filter URLs keep working. The
`?filter[name][op]=...` query parameter is parsed via
`FilterOperator::tryFrom($value) ?? FilterOperator::Eq` at the
`AdminContextResolver` boundary — unknown / typo'd operators
silently fall back to `Eq` exactly like they did in v0.5.

## BREAKING #2 — `BatchableDataSourceInterface` removed

### What changed

`Polysource\Core\DataSource\BatchableDataSourceInterface` is gone.
The single declared method `findMany(array $ids): array<DataRecord>`
no longer has a contract.

### Why

ADR-011 item A1. Pure speculation since v0.1 — zero implementers
across the 6 shipped adapters, zero callers in the monorepo or in
known host apps. Maintaining it through v1.0 would have frozen a
promise no one was keeping.

### How to migrate

If your custom adapter implemented `BatchableDataSourceInterface`:

```diff
- use Polysource\Core\DataSource\BatchableDataSourceInterface;
+ use Polysource\Core\DataSource\DataSourceInterface;

- final class MyDataSource implements BatchableDataSourceInterface
+ final class MyDataSource implements DataSourceInterface
  {
      public function search(DataQuery $query): DataPage { /* … */ }
      public function find(int|string $id): ?DataRecord     { /* … */ }
      public function count(DataQuery $query): ?int         { /* … */ }
-     public function findMany(array $ids): array
-     {
-         // batched fetch implementation
-         return $this->client->getMultiple($ids);
-     }
  }
```

If your code **called** `findMany()` somewhere (rare — neither the
core engine nor any shipped adapter did), inline the loop:

```diff
- $records = $dataSource->findMany($ids);
+ $records = [];
+ foreach ($ids as $id) {
+     $r = $dataSource->find($id);
+     if (null !== $r) {
+         $records[$id] = $r;
+     }
+ }
```

### What if I really needed batched lookups?

The interface is reintroductible. Two options:

- **v1.x reintroduction**: open an issue with the use case
  (typically a join column where rendering a list of resource A
  requires looking up N records from resource B). The polysource
  team will re-add the interface — it was cut because no real
  caller existed, not because the concept is bad.
- **Roll your own**: declare your own `BatchedXyzInterface` in
  your app; cast the `DataSourceInterface` to it where needed.
  This is the same pattern the adapters use for backend-specific
  surfaces — `polysource/adapter-meilisearch` types on its own
  4-method `MeilisearchIndexInterface` rather than on the official
  client, precisely so hosts can swap the implementation behind a
  contract they control.

## What you can now drop

v0.7.1 ships fixes for two long-standing UX traps. Hosts upgrading
can opportunistically remove their workarounds:

### Drop your custom `GenericField` shim

v0.7.1 ships 5 concrete field types in `polysource/core`:
`TextField`, `IdField`, `BooleanField`, `DateTimeField`,
`CodeField`. Each one is a 5-line wrapper over `FieldTrait` that
points at the matching `polysource/twig-theme` template.

```diff
- use App\Polysource\Field\GenericField;
+ use Polysource\Core\Field\TextField;
+ use Polysource\Core\Field\IdField;
+ use Polysource\Core\Field\DateTimeField;

  public function configureFields(string $page): iterable
  {
-     yield GenericField::new('id', 'ID');
-     yield GenericField::new('name', 'Name');
-     yield GenericField::new('createdAt', 'Created');
+     yield IdField::new('id', 'ID');
+     yield TextField::new('name', 'Name');
+     yield DateTimeField::new('createdAt', 'Created');
  }
```

### Drop `configureFields()` entirely on dev/admin-tier resources

When `configureFields()` returns `[]`, both `IndexController` and
`DetailController` now synthesise fields from the record's
properties — one column per `DataRecord::$properties` key. Good
enough for a "list everything that's in the cache" admin page.

```diff
- public function configureFields(string $page): iterable
- {
-     yield TextField::new('identifier');
-     yield TextField::new('value');
-     yield TextField::new('ttl');
-     yield TextField::new('size');
-     return; // …or simply nothing for the empty-fields path
- }
```

The synthesis explicitly skips `$rawSource` (the `@internal` escape
hatch per [ADR-011 A3](../../adr/0011-pre-v1.0-freeze-checklist.md)),
so adapter-specific shapes don't leak to host templates.

## Validation after upgrade

Run these on your app to catch any missed call site:

```bash
# 1. Composer should resolve cleanly
composer update --with-all-dependencies polysource/*

# 2. PHPStan should flag every leftover string-operator constructor
vendor/bin/phpstan analyse src/

# 3. Run your test suite
vendor/bin/phpunit

# 4. Smoke check the admin pages render
bin/console cache:clear
bin/console debug:router | grep polysource_
curl -ksS -o /dev/null -w "%{http_code}\n" "https://your-admin.example.com/admin/your-resource-slug"
```

(Standalone Polysource resources live at
`{url_prefix}/{slug}` — `/admin/cache-keys`, not
`/admin/polysource/cache-keys`. The `/admin/polysource/*` namespace
belongs to the EasyAdmin bridge.)

If PHPStan is silent and the admin pages render, the upgrade is
done.
