# Installing `polysource/bulk-async`

This page covers the install path for a Doctrine + Symfony Messenger
app. Apps without Doctrine ship their own
`BulkJobStorageInterface` — see [extending.md](./extending.md).

## 1. Composer

```bash
composer require polysource/bulk-async
```

Requires `polysource/core`, `polysource/symfony-bundle`, and
`symfony/messenger`. Optional: `symfony/mercure` for live SSE
progress (the polling fallback works without it).

## 2. Register the bundle

Add to `config/bundles.php`:

```php
return [
    // …existing bundles…
    Polysource\BulkAsync\PolysourceBulkAsyncBundle::class => ['all' => true],
];
```

Discoverable via `bin/console polysource:plugins:list` (per
[ADR-018](../../adr/0018-admin-plugin-interface-and-public-contracts.md)).

## 3. Map the entity

Tell DoctrineBundle where to find the bulk-job entity. In
`config/packages/doctrine.yaml`:

```yaml
doctrine:
    orm:
        mappings:
            PolysourceBulkAsync:
                is_bundle: false
                type: attribute
                dir: '%kernel.project_dir%/vendor/polysource/bulk-async/src/Job/Doctrine'
                prefix: 'Polysource\BulkAsync\Job\Doctrine'
                alias: PolysourceBulkAsync
```

## 4. Create the table

```bash
# Production: generate a migration and review it.
bin/console doctrine:migrations:diff
bin/console doctrine:migrations:migrate

# Dev / test: schema:create works for fresh DBs.
bin/console doctrine:schema:create
```

The resulting `polysource_bulk_jobs` table:

| Column | Type | Notes |
|---|---|---|
| `id` | `string(36)` | UUID v7 generated by `AsyncBulkActionDispatcher` |
| `created_at` | `datetime_immutable` | UTC; indexed |
| `resource_name` | `string(120)` | resource slug — e.g. `failed-messages` |
| `action_name` | `string(120)` | the original bulk action's slug |
| `actor_id` | `string(120)` | matches `UserInterface::getUserIdentifier()`; indexed jointly with `created_at` |
| `record_ids_json` | `text` | JSON `list<string>` of ids the job targets |
| `status` | `string(16)` | `pending` / `running` / `completed` / `failed` / `cancelled`; indexed |
| `processed_count` | `integer` | live counter; updated every 5 records or 500 ms |
| `failed_count` | `integer` | counter; rolls into terminal status (Failed if ≥ 1) |
| `started_at` | `datetime_immutable` nullable | stamped when worker flips to Running |
| `completed_at` | `datetime_immutable` nullable | stamped on terminal status |
| `error_message` | `text` nullable | up to 8 KiB; truncated server-side |

3 indexes optimise the canonical queries (chronological scrolling,
"my recent jobs", "all running jobs across the system").

## 5. Configure the Messenger transport

`polysource/bulk-async` ships no transport on its own — hosts wire
their own. The simplest option is the Doctrine transport (you already
have Doctrine for the bulk-job storage, no new dep).

```yaml
# config/packages/messenger.yaml
framework:
    messenger:
        transports:
            polysource_bulk_async:
                dsn: 'doctrine://default?queue_name=polysource_bulk_async'

        routing:
            'Polysource\BulkAsync\Messenger\BulkJobMessage': polysource_bulk_async
```

Then start a worker (under your supervisor of choice — systemd,
Supervisor, `php bin/console messenger:consume` in a loop):

```bash
bin/console messenger:consume polysource_bulk_async --time-limit=3600
```

For higher throughput hosts switch to Redis or AMQP — same routing
key, different transport DSN.

## 6. Import the JSON progress route

Add to `config/routes.yaml`:

```yaml
polysource_bulk_async:
    resource: '@PolysourceBulkAsyncBundle/Resources/config/routes.php'
    type: php
```

This exposes `GET /admin/bulk-jobs/{id}/progress` returning the
canonical progress JSON shape — the Stimulus polling fallback uses
this when Mercure isn't available.

## 7. Permission gates

Two attributes, both blanket — wire voters as you would for any other
Polysource permission:

| Attribute | Purpose |
|---|---|
| `POLYSOURCE_BULK_JOB_VIEW` | List the dashboard, hit the JSON progress endpoint, subscribe to Mercure topics. |
| `POLYSOURCE_BULK_JOB_CANCEL` | Run the inline `cancel` action on a Pending / Running job. |

```php
final class BulkJobVoter extends Voter
{
    protected function supports(string $attribute, mixed $subject): bool
    {
        return \in_array($attribute, ['POLYSOURCE_BULK_JOB_VIEW', 'POLYSOURCE_BULK_JOB_CANCEL'], true);
    }

    protected function voteOnAttribute(string $attribute, mixed $subject, TokenInterface $token, mixed $vote = null): bool
    {
        return \in_array('ROLE_OPS', $token->getRoleNames(), true);
    }
}
```

Or extend an existing `POLYSOURCE_*` blanket voter (the `messenger-demo`
grants every `POLYSOURCE_*` attribute to `ROLE_ADMIN`).

## 8. Optional — wire Mercure for live SSE

If you already run a Mercure hub, register the standard
`MERCURE_PUBLIC_URL` + `MERCURE_JWT_SECRET` env vars per the
`symfony/mercure` docs. `MercureBulkJobBroadcaster` auto-registers
when the Hub service exists; it publishes on the topic
`polysource/bulk-jobs/{id}` with the same JSON shape as the polling
endpoint.

The Stimulus controller picks Mercure over polling automatically when
the template provides a `mercureTopic` — see
[walkthrough.md](./walkthrough.md).

## 9. Smoke-test

```bash
# 1. Dispatch a job through the dispatcher (tinker / a controller):
$dispatcher->dispatch($resource, $bulkAction, ['rec-1', 'rec-2'], 'alice');

# 2. Watch the worker pick it up:
bin/console messenger:consume polysource_bulk_async -vv

# 3. Visit /admin/bulk-jobs to see the live row.
```
