# Internationalisation (i18n) — translations and locale overrides

Polysource ships with **English + French translations** for every
user-facing string across 7 packages. Symfony auto-discovers the
files at boot — hosts don't need any configuration to get
translated UI in either locale.

This page covers:

1. What ships out of the box
2. How to add a new locale (Spanish, German, …)
3. How to override a single key without forking the package
4. Translation-file conventions used across the codebase

## 1. What ships out of the box

| Package | Domain | EN | FR | Coverage |
|---|---|---|---|---|
| `polysource/easyadmin-filter-bridge` | `PolysourceEasyAdminFilterBridge` | ✓ | ✓ | Chips bar, save modal, column-visibility |
| `polysource/filter` | `PolysourceFilter` | ✓ | ✓ | Saved-views dropdown, save-modal, scope labels, defaults |
| `polysource/symfony-bundle` | `Polysource` | ✓ | ✓ | Standalone admin shell — navigation, actions, errors |
| `polysource/bulk-async` | `PolysourceBulkAsync` | ✓ | ✓ | Async bulk-action progress + outcome flashes |
| `polysource/search` | `PolysourceSearch` | ✓ | ✓ | Command-palette labels |
| `polysource/widgets` | `PolysourceWidgets` | ✓ | ✓ | Dashboard widget chrome |
| `polysource/workflow-bridge` | `PolysourceWorkflowBridge` | ✓ | ✓ | Transition action labels |

Each package's translation files live at
`Resources/translations/<Domain>.<locale>.yaml`. Symfony's
`TranslatorBundle` auto-discovers them via the bundle path — no
`framework.translator.paths` config needed in the host.

The host's `framework.default_locale` config decides which locale
is served (Symfony auto-detects from `Accept-Language` when
`framework.set_locale_from_accept_language: true`).

## 2. Add a new locale

To add Spanish, create:

```
config/translations/PolysourceFilter.es.yaml
```

(at the **host level**, not in the package). Copy the keys from
`vendor/polysource/filter/Resources/translations/PolysourceFilter.en.yaml`
and translate the values. Repeat for every Polysource package
whose UI you want translated:

- `PolysourceEasyAdminFilterBridge.es.yaml`
- `PolysourceFilter.es.yaml`
- `Polysource.es.yaml`
- … (whatever's relevant for your stack)

Host-level translation files take precedence over package-shipped
ones (Symfony merges by reverse-priority of registered paths,
with the host's `translations/` dir at the top of the stack).

### Why YAML and not XLIFF?

YAML is human-editable, diffs cleanly in PRs, doesn't need
specialised tooling. XLIFF is the right choice if you have
professional translators using Trados / memoQ / Crowdin — convert
via `bin/console translation:extract` or any YAML→XLIFF script.
Polysource is YAML-only out of the box; hosts can ship XLIFF
overrides without converting the originals.

## 3. Override a single key

To change a label without translating an entire locale, create a
host-level YAML file with **only the keys you want to override**:

```yaml
# translations/PolysourceFilter.fr.yaml
polysource:
  saved_views:
    modal:
      title: 'Enregistrer comme rapport'   # was 'Enregistrer comme vue'
```

Missing keys fall through to the package-shipped translations.
You don't need to redeclare unchanged keys.

The reverse-priority lookup means **your override always wins
when both files define the same key** — there's no per-domain
fallback config required.

## 4. Conventions

Keys are namespaced under a top-level `polysource:` prefix to
avoid clashes with the host's own keys:

```yaml
polysource:
  filter:
    chips:
      heading: 'Filtres actifs'
      clear_all: 'Tout effacer'
  saved_views:
    modal:
      title: 'Enregistrer la vue'
      name: 'Nom'
      scope: 'Visibilité'
```

Plurals use Symfony's `IntlMessageFormatter` syntax (or the
legacy explicit pipe form). The bulk-async package has the
richest examples:

```yaml
polysource:
  bulk_async:
    progress:
      summary: '{count, plural, =0 {No items} =1 {1 item} other {# items}} processed'
```
