## r/symfony post

```
Title: I shipped Polysource — Symfony admin for everything that
       isn't a Doctrine entity

Hey r/symfony,

EasyAdmin is great when your data is in Doctrine. It struggles when
it isn't. After hitting that wall on a Messenger failed-queue
dashboard, a Redis cache inspector, and a "list all S3 invoices"
ops view — three separate tickets that all needed the same admin
UX — I built Polysource.

Polysource is a Symfony admin engine for resources that DON'T live
in a Doctrine ORM database. Six built-in adapters in v0.1:

  - polysource/adapter-messenger    Symfony Messenger failed
                                    transports (retry, dismiss,
                                    purge, retry-all)
  - polysource/adapter-doctrine     Read-only views on Doctrine
                                    entities you don't want in EA
  - polysource/adapter-redis        Redis hash collections (feature
                                    flags, cache, sessions)
  - polysource/adapter-flysystem    S3 / Azure / GCS / local files
                                    via Flysystem 3 + AsyncAws
  - polysource/adapter-http         External REST APIs (Stripe,
                                    GitHub, internal microservices)
  - polysource/adapter-meilisearch  Meilisearch indexes (browse,
                                    search, manual corrections)

Plus 5 cross-cutting capabilities:

  - polysource/audit            GDPR Art. 30 / HIPAA-compliant audit
                                trail with CSV export
  - polysource/workflow-bridge  Symfony Workflow integration with
                                state chips + transition buttons
  - polysource/widgets          KPI / list / chart dashboards
  - polysource/search           Cmd+K command palette across resources
  - polysource/bulk-async       Bulk actions via Messenger with live
                                Mercure progress + cancellation

It cohabits with EasyAdmin in the same Symfony app — EA owns the
Doctrine entities it's good at, Polysource owns the rest. ADR-012
explains the dual-product positioning in detail.

A runnable showcase exercising all 15 packages in a single Symfony
7.4 app:

  git clone git@github.com:polysource/polysource.git
  cd polysource
  make showcase
  open http://localhost:8084

(8-service Docker stack, login admin@shop.co / shopco. Fresh fixtures
load 200 products, 1000 orders, 50 failed messages, 300 login
attempts, 30 cache keys, 15 S3 files, 200 Meilisearch docs.)

14-step screenshotted walkthrough:
  https://github.com/polysource/polysource/blob/main/docs/user/showcase-tour.md

The packages are MIT, on Packagist, supporting Symfony 6.4 LTS / 7.4
LTS, PHP 8.1+ (with the showcase running on the modern stack: PHP 8.4 +
Sf 7.4 + Doctrine ORM 3 + Foundry 2 + AssetMapper).

Happy to answer questions, take feedback, accept PRs. Issues +
discussion welcome.

— Polysource maintainer
```

## What NOT to do

- ❌ **Do not lead with "EasyAdmin replacement"** — it isn't, and the
  audience for "Doctrine admin replacement" is small + hostile to
  newcomers. Lead with the **non-Doctrine** angle.
- ❌ **Do not announce both Announcement A and B on the same day.**
  The two messages compete for attention; space them by 1-2 weeks
  so each lands cleanly.
- ❌ **Do not over-promise on v0.1 polish.** Ship known limitations
  honestly: empty `configureFields()` on Polysource resources (v0.2
  topic), no domain-aware permission voter (Phase G ships flat
  attribute → role mapping, see PolysourceShowcase code), Panther
  cookie-sync deferred to a polish phase. Each one has an ADR
  pointing at the post-v0.1 plan.
