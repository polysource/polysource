# ADR-011 — Pre-v1.0 API freeze checklist

- **Date** : 2026-05-02
- **Statut** : Accepté (vivant — sera fermé au tag v1.0.0)
- **Décide pour** : v0.1+ → v1.0

## Contexte

Une revue exhaustive du codebase fin Phase 7 (4 agents — quality, security,
architecture, silent-failures) a remonté plusieurs items de **resserrement
d'API publique**. Ils ne bloquent pas la release v0.1.0 (les CRITICAL et
HIGH ont été traités dans le commit `775f48a`), mais doivent être tranchés
**avant** que `v1.0.0` ne fige les contrats.

Cet ADR sert de checklist vivante. Chaque item est repris ici avec :
- la justification du report,
- le critère de fermeture (qu'est-ce qui doit être vrai pour le retirer
  de la liste),
- la fenêtre de tir (quelle phase doit l'adresser).

À chaque item retiré, **mettre à jour la section "Statut" du fichier**.
Quand la liste est vide, taguer v1.0.0.

## Décisions (par item)

### A1 — `BatchableDataSourceInterface` : couper ou prouver

**État** : interface définie dans `polysource/core` mais zéro
implémenteur, zéro consommateur dans v0.1. Pure spéculation.

**Critère de fermeture** : un adapter v0.2 (probablement
`polysource/adapter-doctrine`) implémente `findMany()` ET au moins un
controller / service appelle effectivement la méthode pour éviter un
N+1 démontré. Sinon, **supprimer l'interface** au tag v1.0 — quitte à
la réintroduire en v1.x quand un cas réel arrive.

**Fenêtre** : v0.2 (release de l'adapter Doctrine).

### A3 — `DataRecord::$rawSource: mixed` : tightening — ✅ FERMÉ (2026-05-15, v0.7)

**État** : escape hatch typé `mixed` qui permet aux templates et
adapters de downcaster vers `Envelope`, entité Doctrine, etc. C'est
exactement la "leakage de type de stockage" interdite par
l'architecture (cf. ADR-013 + ADR-007 sur l'absence de dépendance Symfony côté `core`). Une
fois shippé en `mixed`, downstream code va s'y accrocher.

**Options** :
1. Marquer `@internal` pour adapter authors uniquement (cheap).
2. Remplacer par `getRaw(string $expectedType): object` qui throw sur
   mismatch (typed escape hatch, plus défendable).
3. Supprimer la propriété (le `core` n'en a aucun usage légitime —
   les adapters peuvent sous-classer `DataRecord` si vraiment).

**Décision** : option 1 retenue. Aucun consumer interne ne touche à
`$rawSource` (grep complet : zéro occurrence de `->rawSource` dans
le monorepo hors le constructeur). Marquer `@internal` documente
l'intention (escape hatch adapter-author-only, hors SemVer surface
v1.0) sans imposer un refactor inutile. Option 2 reste disponible
en v1.x si un cas réel émerge.

**Implémentation** : docblock `@internal` ajouté au constructor de
`DataRecord` en v0.7.0 — pointe vers ADR-013 et précise l'exemption
SemVer.

### A4 — `FilterCriterion::$operator: string` → enum

**État** : opérateur de filtre passé comme chaîne libre (`'eq'`,
`'gt'`, `'like'`, etc.). La docblock note explicitement que la
sémantique de `like` varie par adapter (R17 dans les risques internes).
Un enum tranche le débat et donne PHPStan/IDE le pied pour vérifier.

**Critère de fermeture** : `enum FilterOperator: string` exposé dans
`polysource/core` ; `FilterCriterion::$operator` typé. Migration
PHP 8.0 : l'enum reste convertible en classe-constantes (cf. ADR-007).

**Fenêtre** : v0.5 (en même temps que les premières filter
implementations sortent).

### A6 — `ResourceInterface::configureSearch()` : décider — ✅ FERMÉ (2026-05-15, v0.7)

**État** : la doc cible (`docs/architecture/target-architecture.md`
§6.2.1) liste `configureSearch()` parmi les méthodes attendues, mais
l'interface réelle ne l'expose pas. `DataQuery::$searchText` existe
côté core, donc le concept est partiel.

**Options** :
1. Ajouter `configureSearch(): SearchableConfig` à l'interface — risque
   d'over-design pour un besoin qu'aucun adapter n'a encore exprimé.
2. Retirer la mention de `configureSearch()` de la doc cible.
3. Laisser un hook `setCustomOption('searchable_properties', [...])` sur
   les fields, sans nouvelle méthode d'interface.

**Décision** : option 2. La recherche est portée par
`DataQuery::$searchText` (champ déjà présent côté core) et par
`polysource/search` (palette Cmd+K, ADR-023) — aucun adapter n'a
demandé un hook `configureSearch()` en 6 mois d'usage, et l'ajouter
préventivement va à l'encontre de la discipline YAGNI. Le hook
`setCustomOption('searchable_properties', [...])` (option 3) reste
disponible pour les besoins ad hoc sans changer l'interface
publique.

**Implémentation** : `configureSearch(Search $search): Search` retiré
de `docs/architecture/target-architecture.md` §6.2.1 en v0.7.0.

### A8 — `AdminContext` : décomposition future en sous-VOs — ✅ FERMÉ (2026-05-15, v0.7)

**État** : 7 propriétés sur 10 autorisées par ADR-004. Évolutions
prévisibles en v0.2/0.3 : `?CsrfToken`, `?array $flashes`,
`string $referer`, `?array $audit_metadata`. On franchira le seuil
avant longtemps.

**Critère de fermeture** : décomposition (ex.
`AdminContext { request: RequestContext, audit: AuditContext, ... }`)
définie dans une ADR avant que la 8e propriété soit ajoutée. Pas
d'urgence pour v1.0 — mais **planifier** est l'objectif ici.

**Décision** : ADR-029 écrite (planification, non implémentée). Définit
la structure cible 5-VOs (`RequestContext`, `ResourceContext`,
`UserContext`, `QueryContext`, `PresentationContext`), le critère de
déclenchement (1er PR qui voudrait ajouter une 8e propriété), et la
stratégie de migration en 3 phases. Le code reste à 7 props en v0.7 —
on n'a pas franchi le seuil.

**Référence** : [ADR-029](./0029-admin-context-decomposition.md).

### L4 — `DataPage::isEmpty()` consomme un Generator one-shot — ✅ FERMÉ (2026-05-15, v0.7)

**État** : `isEmpty()` dernière branche fait
`iterator_to_array($this->items, false)` sans cacher le résultat. Pour
un `\Generator` passé comme `items`, un `asArray()` ultérieur retourne
`[]`. La docblock mentionne le risque mais le `final readonly`
empêche le caching post-construction.

**Options** :
1. Materialiser `$items` au constructor si `Traversable && !Countable`
   (perte d'avantage du lazy iterator).
2. Documenter plus visiblement (déjà fait à 70%).
3. Bouger vers une factory statique
   `DataPage::fromGenerator(callable): self` qui materialise une seule
   fois.

**Décision** : option 2. Materialiser au constructor (option 1) tue
l'avantage des sources cursor-based qui veulent streamer une grosse
page sans charger en RAM. La factory (option 3) ajoute de la surface
d'API pour un cas qu'un docblock visible résout aussi bien. Le
docblock de `isEmpty()` est ré-écrit en v0.7.0 avec une section
"⚠️ Generator consumption warning" + 3 patterns d'appel sûrs +
recommandation explicite que les producers passent `$total` pour
éviter le branch unsafe.

**Implémentation** : `packages/core/src/Query/DataPage.php::isEmpty()`
en v0.7.0.

## Conséquences

### Positives

- Aucun item perdu entre la review Phase 7 et le tag v1.0.
- Les contributeurs ouvrant un PR sur un de ces items peuvent référencer
  ADR-011 pour le contexte.
- Pression saine pour ne pas ajouter de la surface d'API spéculative
  ("on aura le temps de couper en v1.0") sans suivi.

### Négatives

- Un item de plus à maintenir. Mitigation : le check est fait au tag
  v1.0, pas chaque release.
